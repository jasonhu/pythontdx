# 06 · 踩坑笔记

> 这里记录的都是**本项目真实踩到并解决**的问题，不是从搜索引擎抄来的清单。
> 每一条都包含「现象 → 原因 → 解决」，方便以后回查。

## 1. PowerShell 里 `npm` 报「running scripts is disabled」

**现象**

```
npm : File C:\Program Files\nodejs\npm.ps1 cannot be loaded because
running scripts is disabled on this system.
```

**原因**
Windows PowerShell 默认执行策略是 `Restricted`。在 PowerShell 里输入 `npm` 时，
解析到的其实是 `npm.ps1`（而不是 `npm.cmd`），于是被执行策略拦下。

**解决**

```powershell
npm.cmd install                            # 方案 A：绕过 .ps1
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned   # 方案 B：一劳永逸
```

## 2. Electron 装好了，但没有 `electron.exe`

**现象**
`npm install` 成功，但 `node_modules/electron/dist/` 不存在，运行时报
`Electron failed to install correctly`。

**原因**
**Electron 44 已经取消了 `postinstall` 脚本**，改成「第一次被 `require` 时惰性下载」。
所以 `npm install` 之后看不到二进制是正常的，它会在第一次 `npm run dev` 时才去下载。
（顺带一提：新版 npm 默认还会拦截依赖的 install scripts，esbuild 之类的包也会被拦，
但 esbuild 的平台二进制是通过 optionalDependencies 装的，通常不受影响。）

**解决**

```powershell
$env:ELECTRON_MIRROR = 'https://npmmirror.com/mirrors/electron/'
$env:ELECTRON_CUSTOM_DIR = '{{ version }}'
node node_modules/electron/install.js
```

其中国内网络下 **`ELECTRON_MIRROR` 是必须的**（GitHub Releases 基本不可达），
而 `ELECTRON_CUSTOM_DIR={{ version }}` 也是必须的——npmmirror 的目录结构是
`/44.4.3/`，不是 GitHub 的 `/v44.4.3/`。

项目已经把这两项写进 `.npmrc`，npm 会把它们注入成 `npm_config_*` 环境变量传给子进程，
所以正常 `npm install` 就能自动走镜像。

**验证镜像配置是否生效**：

```powershell
npm run env | Select-String electron
# npm_config_electron_custom_dir={{ version }}
# npm_config_electron_mirror=https://npmmirror.com/mirrors/electron/
```

## 3. 分时接口 `JSON.parse` 失败

**现象**
实时行情正常，但分时图一直报「行情接口返回了非预期的数据格式」。

**原因**
我画蛇添足地给 URL 加了个 `&_var=min_data_sh600519` 参数用来「防缓存」。
**腾讯的 JSON 接口只要看到 `_var`，就会返回 JSONP**：

```
var min_data_sh600519={"code":0,"data":{...}};
```

这已经不是合法 JSON 了。

**解决**
去掉 `_var` 参数即可。缓存交给自己的 TTL 缓存层去做，不要动上游的参数。

## 4. Solid 的 `createResource` 因为 source 身份变化而反复请求

**现象**
主进程每 3 秒推一帧行情，图表却也跟着每 3 秒重新拉一次数据。

**原因**
`createResource` 内部把 source 包成了 `createMemo(source)`（见 `solid.cjs`）。
读 `props.code` 会订阅父组件传下来的响应式 getter，
而父组件每 3 秒就会产生一个新的 quote 对象——虽然 `.code` 字符串没变，
但 source 每次返回的都是**新的对象字面量**，引用不等，于是每次都被判定为「变化了」。

**解决**
用 `createMemo` 把原始值稳定下来（memo 默认做值比较）：

```ts
const code = createMemo(() => props.code)   // 字符串没变 → 不向下游传播
// ...
createResource(() => ({ code: code(), tab: tab(), ... }), fetcher)
```

**验证方式**：在 source 里打日志，正常情况应该只有「挂载时 1 次 + 定时刷新 N 次」。
我们当时看到的是 6 次（每一次行情推送都触发），加上日志后立刻定位。

## 5. Solid 1.9 的 `createResource` 返回值变了

**现象**

```
error TS2339: Property 'refetch' does not exist on type 'Resource<ChartData>'.
```

**原因**
Solid 1.9 的类型定义是：

```ts
export type ResourceReturn<T, R> = [Resource<T>, ResourceActions<T | undefined, R>]
export type ResourceActions<T, R> = { mutate: Setter<T>; refetch: (info?: R) => ... }
```

`refetch` / `mutate` 在**元组的第二个元素**上，不在 resource 本身。

**解决**

```ts
const [data, { refetch }] = createResource(source, fetcher)
```

**附带发现**：resource 处于 `errored` 状态时，**直接调用 `data()` 会抛出异常**
（`if (err !== undefined && !pr) throw err`）。
所以读取前要先判 `data.error`，或者在 `<Show when={!data.error}>` 的 fallback 里避开读取。

## 6. Solid JSX 里的 SVG 属性必须用 kebab-case

**现象**

```
error TS2322: Property 'strokeWidth' does not exist on type 'SvgSVGAttributes<SVGSVGElement>'.
Did you mean '"stroke-width"'?
```

**原因**
React 用的是驼峰（`strokeWidth`），但 Solid 直接映射到真实 DOM/SVG 属性，用的是
kebab-case（`stroke-width`）。

**解决**
统一写 `'stroke-width'`。本项目还顺手把它收进了一个 `svgProps()` 工厂函数，
让所有图标共享同一套规格，个别图标想调细描边只需传第二个参数。

## 7. `ResizeObserver loop completed with undelivered notifications`

**现象**
控制台反复出现这条告警。

**原因**
`ResizeObserver` 的回调里写信号 → 触发重绘 → 尺寸再次变化 → 又触发回调。
虽然浏览器会自动容错（不会真的死循环），但告警很吵。

**解决**
在回调里做**值比较**，尺寸真的变了才写信号：

```ts
setSize((prev) => (prev.width === w && prev.height === h ? prev : { width: w, height: h }))
```

## 8. 港股的字段布局和 A 股完全不同

**现象**
把 A 股的解析逻辑直接套到港股上，市净率位置显示的是 `TENCENT`，涨停价位置显示的是 52 周高点。

**原因**
A 股响应有 **88** 个字段，港股只有 **78** 个，而且从下标 30 往后含义就分叉了：
港股下标 30 是 `2026/09/21 16:08:36`（带斜杠），A 股是 `20260921161437`（纯数字）；
港股 46 是英文名、48/49 是 52 周高低。

**解决**
按市场分派到两个解析函数（`buildAShareQuote` / `buildHkQuote`），
拿不到含义的字段一律置 `undefined`，界面用统一的 `—` 占位。
时间解析也要同时兼容两种格式，并统一按东八区换算成时间戳。

**额外注意**：港股成交量单位是**股**，A 股是**手**；
成交额 A 股字段 37 是**万元**，港股是**元**。

## 9. 接口失败会引发重试风暴

**现象**
分时接口报错的那次调试里，日志里短时间内出现了大量重复的 `trend:minute` 请求。

**原因**
上游失败 → 渲染层重新求值 → 再次 invoke → 主进程再打一次上游。
因为失败结果不进缓存，每一次都会真的发出网络请求。

**解决**
在缓存层做 **同 key 并发请求合并**：把在途的 Promise 也存起来，
同一时刻同一个 key 最多只有一个真实请求，无论上游并发调用多少次。
失败时**不写缓存**，但一定要清掉在途标记，否则后续请求会被永久挂住。

```ts
const inFlight = this.pending.get(key)
if (inFlight) return inFlight
```

这是本项目里「防御性设计」价值最高的一个改动。

## 10. 无边框窗口的按钮点不动

**现象**
自绘标题栏做完，窗口能拖动，但最小化/关闭按钮点不动。

**原因**
`-webkit-app-region: drag` 会把整个区域变成「窗口拖拽热区」，
Chromium 不再把鼠标事件派发给里面的元素。

**解决**
给所有交互元素显式声明：

```css
.titlebar__actions,
.win-controls,
.search-wrap {
  -webkit-app-region: no-drag;
}
```

**排查技巧**：如果某个按钮「看起来能 hover 但点击无反应」，
先怀疑它的祖先里有 `drag` 区域。

## 13. 分时接口的 `qt` 快照嵌在 `data.<代码>` 里，不在顶层

**现象**
分时图上价格线画得出来，但浮层里 `涨跌幅` 永远显示 `—%`，`涨跌额` 显示成一个巨大的数（等于价格本身）。

**原因**
我把 `qt` 当成了响应的顶层字段：

```ts
// ❌ 错的
const snapshot = raw.qt?.[code] ?? []
```

实际结构是嵌在 `data.<代码>` 里的：

```jsonc
{ "data": { "sh600519": { "data": { ... }, "qt": { "sh600519": [...] } } } }
```

于是 `snapshot` 是空数组 → `Number(undefined) || 0` → **昨收 = 0**
→ 涨跌额 = 价格 − 0 = 价格本身，涨跌幅 = `∞` → 界面上被格式化成 `—%`。

**解决**

```ts
const body = raw.data?.[code]
const snapshot = body?.qt?.[code] ?? []
```

**这个 bug 是被截图抓出来的**，不是被类型检查抓出来的——因为 `raw.qt?.[code]`
在类型上完全合法（可选属性），只是永远取不到值。
它现在有一个专门的回归测试（`parse.test.ts` → `昨收从 data.<代码>.qt 里取（回归测试）`）。

**教训**：解析第三方报文时，`?.` 会掩盖「路径写错」这类错误。
关键字段要么用测试锁住，要么在解析函数里对异常值（这里是 0）显式兜底。

## 14. `000858`（五粮液）被判成了沪市

**现象**
单元测试报错：`expected 'SH' to be 'SZ'`。

**原因**
我原本写了一条「000 开头且不是 000001 就当沪市（上证系指数多为 000xxx）」的规则。
但 `000xxx` 绝大多数是**深市主板股票**（000001 平安银行、000002 万科A、000858 五粮液），
上证指数只占其中极少数几个。

**解决**
`000xxx` 一律按深市股票解释；要查指数必须显式带前缀（`sh000001`、`sh000300`）。

**教训**：遇到有歧义的编码规则时，选「绝大多数情况正确 + 少数情况有明确逃生通道」的方案，
而不是试图用规则把所有情况都猜对。**这条也是被测试逼出来的**。

## 15. Solid 的 `ref={变量}` 会被 ESLint 判为「变量从未被赋值」

**现象**

```
error  'inputElement' is always 'undefined' because it's never assigned  no-unassigned-vars
```

**原因**
Solid 确实支持这种写法，但它是**编译器的隐式赋值**：

```tsx
let inputElement: HTMLInputElement | undefined
;<input ref={inputElement} /> // 编译器偷偷生成赋值语句
```

静态分析工具看不到这个赋值，于是合理地认为变量永远是 `undefined`。

**解决**
改用显式回调，行为毫无歧义，可读性也更好：

```tsx
<input
  ref={(element: HTMLInputElement) => {
    inputElement = element
  }}
/>
```

## 16. 闭包捕获派生值 → 图表切换天数后横轴不更新

**现象**
ESLint 的 `solid/reactivity` 报警：

```
'totalSlots' captures the value of the reactive variable 'days' at setup,
but a returned function reads the capture later — it will never update.
```

**原因**
在 memo 里算出一个数字，再让返回出去的函数去读它：

```ts
const geometry = createMemo(() => {
  const totalSlots = days().length * DAY_SLOTS - 1
  return { x: (slot) => slot / totalSlots } // ⚠️ 读的是创建那一刻的闭包变量
})
```

在这个例子里，memo 每次重跑都会重建闭包，所以**实际上是对的**。
但这条规则抓的是同一类模式里真正出错的情形：
只要 `x` 被单独传递出去、活过了 memo 的那一轮，它就会永远停留在旧值上。

**解决**
按规则的建议，在函数内部重新读取响应式源：

```ts
x: (slot) => PAD.left + (slot / Math.max(1, days().length * DAY_SLOTS - 1)) * plotW
```

**教训**：不要在返回值里「捕获」派生值，要么传值本身，要么在函数里现读。
这个开销可以忽略，换来的是绝不会过期。

## 17. 用 `createMemo` 做副作用

**现象**

```
error  For proper analysis, a variable should be used to capture the result of this function call
```

**原因**
我为了「只在读数变化时通知外部」，写了一个裸的 `createMemo(() => { props.onHover(...) })`。
memo 的语义是「派生一个值」，拿它当副作用钩子用是坏味道，
而且因为没有接收返回值，读者也无法判断这里到底在算什么。

**解决**
用 `createEffect` + `on`，语义明确，触发时机也更准（只在依赖变化时执行）：

```ts
createEffect(
  on(hovered, (current) => {
    props.onHover?.(current ? { ... } : null)
  })
)
```

## 18. 新增一个 IPC 通道要改几个地方

**现象**
加了「五日分时」之后，渲染层调用 `api.trend.fiveDay(...)` 直接报 `undefined is not a function`。

**原因**
新增一个通道实际要同步改 **5 个地方**，漏一个就是运行时错误：

1. `src/shared/ipc.ts` —— 通道名常量 `IPC.xxx`
2. `src/shared/ipc.ts` —— `StockLensApi` 接口里加方法签名
3. `src/preload/index.ts` —— `ipcRenderer.invoke` 的实现
4. `src/main/ipc.ts` —— `ipcMain.handle` 的注册
5. `src/main/services/**` —— 真正的业务实现

**好消息**：第 2 步是类型契约，漏了第 3 步会**编译报错**（对象缺少属性），
第 4、5 步漏了会在调用时报「No handler registered」。
也就是说，只要认真跑 `npm run typecheck`，这类问题基本不会跑到运行时。

**教训**：这就是「共享类型契约」的价值——把「字符串写错」和「漏实现」变成编译期错误。

## 19. 打包时卡在下载 NSIS 工具链

**现象**
`npm run build:win` 走到一半卡住，然后报网络错误。日志停在：

```
• building        target=portable file=release\0.3.0\...
• downloading     url=https://github.com/electron-userland/electron-builder-binaries/releases/...
```

**原因**
`npm install` 时下载 Electron 二进制走的是 `.npmrc` 里的 `electron_mirror`，
但 **electron-builder 打包时用的是另一套下载器**，它要下载 NSIS、7zip、winCodeSign
等工具链，默认仍然指向 GitHub Releases，国内网络不可达。

两件事容易混淆：

| 阶段                | 谁在下                | 环境变量                                                                |
| ------------------- | --------------------- | ----------------------------------------------------------------------- |
| `npm install`       | Electron 自己的下载器 | `ELECTRON_MIRROR` / `electron_mirror`                                   |
| `npm run build:win` | electron-builder      | `ELECTRON_BUILDER_BINARIES_MIRROR` / `electron_builder_binaries_mirror` |

**解决**
在 `.npmrc` 里再补一条：

```ini
electron_builder_binaries_mirror=https://npmmirror.com/mirrors/electron-builder-binaries/
```

npm 会把 `.npmrc` 的键注入成 `npm_config_*` 环境变量并传给子进程，
而 electron-builder 的 `getBinariesMirrorUrl()` 恰好会读
`npm_config_electron_builder_binaries_mirror`，所以配置一次就够了。

**验证是否生效**：重新打包时日志里的下载地址应该变成 `npmmirror.com`。

## 20. 便携版的 `unpackDirName` 并不会缓存解压结果

**现象**
我按官方文档的说明，给 `portable` 目标加了固定解压目录名，
并在配置注释里写下「第二次启动就能复用，冷启动快很多」。
实际测下来**完全没有加速**，热启动和冷启动耗时一模一样。

**原因**
我搞错了 `unpackDirName` 的作用。实测（electron-builder 26 / 2026-09）：

- 它**只决定解压目录的名字**（`%TEMP%\StockLensPortable`），方便排查与手工清理；
- 应用**正常退出时会清理该目录**，所以下次启动依然要完整解压一遍；
- 只有进程被强杀（任务管理器结束任务）时才会残留。

也就是说，「单文件 exe 每次启动都要解压约 368 MB」这件事是**无法回避**的。

**实测数据**（清空 `%TEMP%` 后连续多次测量）：

| 产物                              | 从双击到界面就绪           |
| --------------------------------- | -------------------------- |
| 便携版单 exe                      | **约 2 秒**（3 次均为 2s） |
| `win-unpacked` 里的 exe（无解压） | **约 1 秒**（2 次均为 1s） |

**解决**
接受它，并把真实数字写进文档和配置注释。
结论：单文件免安装只比安装版慢约 1 秒，代价比预想的小；
想要更快就用 NSIS 安装包，想要「一个文件带走」就用便携版。

**第二次踩坑**：我第一次测量时把截图工具里「等待 N 秒再截图」的时间
算进了启动耗时，得出「便携版要 6 秒」的错误结论，并已经写进了配置注释和文档。
后来固定 `delay=0` 重测 3 次才拿到 2s 这个稳定值。
**测量脚本本身的固定开销必须排除掉**，否则量出来的不是被测对象。

**教训**：这是本项目里第二次由「我以为」引发的错误（第一次是 `qt` 的路径）。
**涉及性能或行为的断言，必须实测后再写进注释与文档**——
否则注释会变成误导下一个人的假信息。
这也正是 `PRINCIPLES.md` 里 Q3（声称完成前必须有可复现的证据）存在的原因。

## 21. `STOCKLENS_CAPTURE_DELAY=0` 会让截图抛错、退出码为 1

**现象**
重新打包后复测便携版启动耗时，沿用了第 20 条的写法把截图延迟设为 0
（目的就是排除截图工具的等待时间）。结果进程**退出码是 1、也没有产出截图文件**。
第一反应是「这次打包是不是坏了 / 应用根本没起来」。

**原因**
退出码 1 不是崩溃。`src/main/capture.ts` 里只有截图失败那条路径会 `app.exit(1)`，
其余情况都是 `app.exit(0)`。延迟为 0 时，`capturePage()` 在
`did-finish-load` 之后**同一个 tick** 内执行，页面还没合成首帧，
Electron 抛 `UnknownVizError`。

用 `out/` 产物 + 开发用 Electron 复现（这样主进程控制台可见）：

| 延迟  | 结果                                                              |
| ----- | ----------------------------------------------------------------- |
| `0`   | `[capture] 截图失败： [Error: UnknownVizError]`，退出码 1，无文件 |
| `800` | `[capture] 截图已保存：…`，退出码 0                               |

**解决**

- 只测启动耗时时可以忽略这个退出码：进程此时已经打印过
  `[main] 配置文件：…`，说明引导流程已经跑完；
- 要拿到截图，就必须给页面留出合成时间（`npm run shot` 默认 4 秒）；
- 判断「应用有没有真的起来」**不要只看退出码**，要看有没有产出有效内容——
  本次截图 631 KB / 2558×1640 / 3201 种颜色，且红绿两种涨跌色都存在。

**教训**：退出码 1 在这套工具里是**有明确含义的**（截图失败），
并不是「任何异常都归它」。排查这类问题应该先读一遍自己写的错误分支，
而不是先怀疑打包产物。

## 22. 键盘交互没法截图验证：两个坑都是「量」出来的，不是看出来的

**现象**
给 K 线图加上「`↑` / `↓` 缩放可见根数」之后发现问题：`npm run shot` 只能拍到
**没按键的那一帧**——键盘交互拍不到。于是给截图工具加了一组开关
（点击 / 聚焦 / 注入按键 / 回读文本 / 求值只读表达式），让应用自己把界面点到位、
把键按下去、再把结果读回终端。

工具一上线，就抓到两个我自己没意识到的问题：

| 用例               | 第一次跑出来      | 应该是 | 原因                               |
| ------------------ | ----------------- | ------ | ---------------------------------- |
| `Up,Up`（按 2 下） | 120 根            | 80 根  | 切 tab 重建了 DOM，前 1 个按键被吞 |
| 最小窗口 1024×660  | 图例压到了 tab 上 | 不重叠 | 新加的档位标签把头部挤爆了         |

**原因**

- **按键被吞**：我一开始把「点击（切到日K）」和「聚焦图表」放在同一步里做完。
  但切 tab 会让 SolidJS 卸载分时图、挂载 K 线图，**被聚焦的那个 DOM 节点整个被替换掉了**，
  焦点随之回到 `body`，落在它之后的按键就没有落点。
  改成「点 tab → 等目标元素出现 → 再聚焦 → 按键」之后，按 2 下就是 2 档。
- **头部被挤爆**：`.segmented` 作为 flex 子项**默认会收缩**，头部一超宽，
  tab 自己先被压窄（240 → 201px），图例再压到 tab 上。
  这是量出来的，不是看出来的：`getBoundingClientRect()` 显示
  `seg: 255..456`、`legend: 432..593` —— 两者重叠 24px。

**解决**

- 工具里把「准备界面」和「聚焦」拆成前后两步，并且**等界面就绪之后**才聚焦；
- 档位标签从卡片头部搬到**图表自己的上边距**里（`x = padding.left, y = 12`）：
  那里是天然空白带，永远不会和 tab、图例、蜡烛、网格线抢位置，
  1024 最小窗口下也不必做任何响应式妥协。

**验证**（元素矩形 + SVG 实测，全程没有用眼睛看图）：

| 档位   | SVG 矩形数 | 蜡烛实体宽度 |
| ------ | ---------- | ------------ |
| 160 根 | 321        | 2.17px       |
| 80 根  | 161        | 4.34px       |
| 30 根  | 61         | 11.58px      |

按键序列 `↑↑↓↓` 回到 160 根、`↑` 连按 5 次停在 30 根（到顶不环绕），
都与纯函数的单元测试断言一致。

**教训**：**「看不了图」不应该成为「不验证」的借口。**

## 23. 存了「窗口内的相对下标」，缩放后光标就指向了另一根 K 线

**现象**
用户实测 K 线缩放后反馈：**缩放生效了，但鼠标光标指着的那根 K 线漂移了** ——
按下 `↑` 之后十字光标还停在屏幕上差不多的位置，可它读出来的已经不是原来那一根。

**原因**
状态里存的是**窗口内的相对下标**（`hoverIndex`），窗口一变（160 → 80 根），
同一个下标就指向了另一根 K 线。这是典型的「**状态存了派生量**」：
相对下标 = 绝对下标 − 窗口起点，它应该被算出来，而不是被存起来。

**解决**

1. 光标改存**绝对下标**，窗口内的位置在使用处现算（`absolute - win.start`）；
2. 缩放改为**以光标为锚点**（`zoomWindow()`）：先算锚点在窗口里的比例，
   缩放后反推新起点，让它落在同一个比例上；
3. 光标走到窗口边缘时窗口跟着平移（`stepCursor()`），另加 `End` 一键回最新。

**一个躲不掉的取舍**
「锚点在屏幕上完全不动」与「窗口右侧不留白」互斥：光标贴着最新一根时，
要保持位置就得让窗口滚过最新一根、在右边空出一块。这里选择**贴合数据**，
代价是贴边缩放时光标在屏幕上会挪一点 —— 但它指的仍是同一根。
单测如实描述了这个取舍：中间位置断言比例不变，贴边位置只断言
「光标仍在窗口内、窗口不越界」。

**验证**（端到端实测，读的是浮层里的日期）：

| 按键                   | 档位         | 光标那一根   |
| ---------------------- | ------------ | ------------ |
| `←`                    | 近 160 根    | `2026-09-21` |
| `← ← ←`                | 近 160 根    | `2026-09-17` |
| `← ← ←` + `↑ ↑`        | **近 80 根** | `2026-09-17` |
| `↑↑` + `←` + 79 个 `←` | 近 80 根     | `2026-06-01` |
| `↑↑` + `←` + 81 个 `←` | 近 80 根     | `2026-05-28` |

第三行是关键：**档位从 160 变成 80，光标读出的日期没变**。
第四、五行则证明平移真的发生了 —— 若窗口不平移，两次会停在同一根。

**教训**：**状态里只存「不可推导的量」。** 能由别的状态算出来的值，
存它就迟早和源头不一致 —— 这里表现为「光标指着别人」。

## 24. `sendInputEvent` 的 `keyCode` 要加速器键名，写错不报错、只是没反应

**现象**
用刚做好的按键注入复测光标功能，六个用例**全部没反应**：档位一直是 160 根，
浮层也不出现。唯一生效的是 `End` —— 因为它正好两种写法同名。

**原因**
`window.webContents.sendInputEvent({ keyCode })` 收的是 **Electron 加速器键名**
（`Up` / `Left` / `Esc`），我传的是 DOM 的 `ArrowUp` / `ArrowLeft`。
连一条错误信息都没有：事件发出去了，只是没人认得，**静默失效**。
（先前验证缩放时用的恰好是 `Up,Up`，所以这个坑一直藏着没暴露。）

**解决**
工具里加一张别名表，两种写法都收：

```ts
const KEY_ALIASES = {
  ArrowUp: 'Up',
  ArrowDown: 'Down',
  ArrowLeft: 'Left',
  ArrowRight: 'Right',
  Escape: 'Esc',
  Enter: 'Return'
}
```

**顺带一个方法论**：这类会「静默失效」的工具，必须让它自己把结果**回读**出来。
如果只是「按下键、截张图」，我要么得用眼睛看图（看不了），
要么就会把「没反应」误判成「功能没做」—— 事实上我第一眼就是这么以为的。

**教训**：**外部接口的「名字」最容易静默出错。** 编译器管不到字符串参数，
所以要么把它收窄成联合类型，要么就兼容多种写法。
把要看的东西换算成能读的数——元素矩形、SVG 宽度、文本内容——
一样能发现真实的布局缺陷，而且比肉眼更早、更准（这条正好呼应 `PRINCIPLES.md` 的 Q3）。
