# 02 · 架构设计

## 一、三个进程，三种世界

Electron 应用天然是「三份代码、三个运行时」：

```
┌─────────────────────────────────────────────────────────────────────┐
│  主进程 Main（Node.js 环境）                                          │
│  · 窗口生命周期、菜单、托盘                                            │
│  · 唯一能自由访问网络与文件系统的地方                                   │
│  · 定时器（行情轮询）在这里跑，不受界面节流影响                          │
│                                                                      │
│  src/main/index.ts      入口 / 单实例锁 / 退出前落盘                    │
│  src/main/window.ts     无边框窗口 + 开发期诊断                        │
│  src/main/ipc.ts        所有 IPC 处理器的注册中心                       │
│  src/main/services/*    HTTP、缓存、解析、持久化、轮询                   │
└───────────────────────────┬─────────────────────────────────────────┘
                            │  ipcMain.handle / webContents.send
┌───────────────────────────▼─────────────────────────────────────────┐
│  预加载 Preload（隔离的桥梁）                                          │
│  · 唯一同时能碰到 Node 与 DOM 的地方                                   │
│  · 只暴露一份白名单 API：window.api                                    │
│  · 绝不把 ipcRenderer 本身交出去                                       │
│                                                                      │
│  src/preload/index.ts       contextBridge 白名单                      │
│  src/preload/index.d.ts     window.api 的类型声明                      │
└───────────────────────────┬─────────────────────────────────────────┘
                            │  window.api.*（Promise / 事件订阅）
┌───────────────────────────▼─────────────────────────────────────────┐
│  渲染进程 Renderer（浏览器环境）                                       │
│  · 只有界面与交互，没有 Node 权限                                      │
│  · 状态用 Solid Store 管理，改状态立刻响应，落盘异步进行                 │
│                                                                      │
│  src/renderer/src/App.tsx        布局 + 订阅启动                       │
│  src/renderer/src/stores/*       状态仓库                             │
│  src/renderer/src/components/*   组件（含手绘 SVG 图表）                │
└─────────────────────────────────────────────────────────────────────┘
                    ▲
                    │  类型共享（编译期，不产生运行时代码）
              src/shared/*  types.ts · ipc.ts · market.ts · format.ts
```

### 为什么把网络和定时器放在主进程？

| 放渲染进程                               | 放主进程（本项目的选择）  |
| ---------------------------------------- | ------------------------- |
| 被 CORS 拦截（腾讯接口不返回 CORS 头）   | 无同源限制                |
| 拿不到 GBK 解码能力                      | `TextDecoder('gbk')` 可用 |
| 窗口最小化时被 Chromium 节流，定时器漂移 | 定时器精准                |
| 将来多窗口 / 托盘常驻要重复实现          | 单一数据源，天然共享      |

## 二、IPC 契约：让编译器帮你查错

三个进程共享 `src/shared/` 下的**同一份类型定义**，这是整个项目最重要的工程决策。

```ts
// src/shared/ipc.ts
export const IPC = {
  quoteSnapshot: 'quote:snapshot',
  quoteUpdate: 'quote:update'
  // ...
} as const

export interface StockLensApi {
  quote: {
    snapshot(codes: string[]): Promise<Quote[]>
    subscribe(codes: string[], intervalMs: number): Promise<void>
    onUpdate(listener: (update: QuoteUpdate) => void): () => void
  }
  // ...
}
```

- **通道名用常量**，杜绝「字符串写错但编译通过」；
- **preload 的实现被 `StockLensApi` 约束**，少实现一个方法就报错；
- **渲染层的 `window.api` 也标注同一类型**，调用签名不一致立刻报错。

于是「主进程改了参数、忘了改渲染层」这类问题在 `npm run typecheck` 阶段就会被拦下来。

### 两种通信模式

| 模式       | API                                     | 用在哪                                     |
| ---------- | --------------------------------------- | ------------------------------------------ |
| 请求-响应  | `ipcRenderer.invoke` / `ipcMain.handle` | 一次性取数：K 线、搜索、读写配置、窗口控制 |
| 服务端推送 | `webContents.send` / `ipcRenderer.on`   | 高频行情：主进程按节奏推，渲染层被动收     |

行情选择「推送」而不是「渲染层定时拉」，是因为推送模式下刷新节奏由主进程统一掌控，
可以整体做降频、暂停、并发合并，而不用在每个组件里各写一份 `setInterval`。

## 三、一条行情数据的完整旅程

```
① 界面订阅
   App.tsx: createQuoteStream(() => watchCodes(), () => settings.refreshInterval)
        │  自选股或刷新间隔一变，effect 自动重跑
        ▼
② 过桥
   api.quote.subscribe(codes, intervalMs)          ← preload 白名单
        ▼
③ 主进程
   QuotePoller.setSubscription()
        ├─ 代码没变 → 不打断当前节奏
        ├─ 代码变了 → 立刻 refreshNow() 拉一帧，减少界面空窗
        └─ 重排定时器：交易时段用用户间隔，盘后自动 ≥30s
        ▼
④ 取数（含缓存与重试）
   fetchQuotes(codes)  →  分批(≤60只) →  requestTextWithRetry(url, { encoding: 'gbk' })
        ▼
⑤ 解析
   parseQuotePayload(text) → parseQuoteFields(code, fields)
        ├─ A 股：88 字段布局
        └─ 港股：78 字段布局（部分下标含义不同）
        ▼
⑥ 推送
   poller.emit({ quotes, at }) → webContents.send('quote:update', update)
        ▼
⑦ 渲染层落库
   createQuoteStream 的回调 → setQuoteMap(code, quote)  ← Solid Store
        ▼
⑧ 细粒度更新
   只有读取了该股票字段的 DOM 节点会更新；价格变化触发一次 700ms 的高亮闪烁
```

## 四、状态管理：谁持有什么

| 状态                       | 存放位置                        | 理由                                              |
| -------------------------- | ------------------------------- | ------------------------------------------------- |
| 自选股列表、设置、当前选中 | 渲染层 Store + 主进程 JSON 文件 | 界面操作的响应必须是 **0 延迟**的，落盘只是副作用 |
| 行情快照                   | 渲染层 Store（主进程只做转发）  | 高频数据不在磁盘和 IPC 之间来回搬                 |
| 分时 / K 线                | `createResource` 局部状态       | 生命周期与图表组件一致，切股票自动作废            |
| 窗口尺寸位置               | 主进程 JSON 文件                | 属于「窗口」而不是「界面」                        |
| 在途请求 / TTL 缓存        | 主进程内存                      | 只对网络层有意义                                  |

**写入策略**：渲染层改状态 → 立刻更新 UI → 异步 `api.state.patch()` → 主进程 150ms 防抖 → 临时文件原子替换。
好处是打字、勾选、拖拽这类操作永远不会因为磁盘 IO 卡住。

## 五、持久化设计

```
%APPDATA%/StockLens/stocklens.json
{
  "version": 2,
  "state": {
    "groups": [
      { "id": "default", "name": "自选", "items": [{ "code": "sh600519", "name": "贵州茅台", "market": "SH" }] },
      { "id": "tech", "name": "科技", "items": [] }
    ],
    "activeGroupId": "default",
    "settings": { "refreshInterval": 3000, "theme": "dark", ... },
    "activeCode": "sh600519"
  },
  "window": { "x": 320, "y": 180, "width": 1280, "height": 820 }
}
```

三个细节：

1. **原子写**：先写 `stocklens.json.tmp` 再 `rename` 覆盖。
   `rename` 在同一分区上是原子操作，所以不会出现「写了一半断电 → 配置全丢」。
2. **版本号 + 迁移**：`version` 用来标记数据结构版本。
   v1 的自选股是一个扁平数组，v2 变成了分组。
   迁移策略是**读的时候兼容旧格式、写的时候只写新格式**（`store.ts` 的 `normalizeGroups`），
   用户完全无感知——本项目实际的配置文件就是这样从 v1 平滑升到 v2 的。
3. **引用完整性**：`activeGroupId` 在读入时会校验「这个分组是否真的存在」，
   不存在就回落到第一个分组。否则删掉分组后重启，界面会找不到当前分组。

## 六、安全模型

| 措施                     | 位置                | 作用                                          |
| ------------------------ | ------------------- | --------------------------------------------- |
| `contextIsolation: true` | window.ts           | 页面的 JS 与 preload 的 JS 运行在隔离的上下文 |
| `nodeIntegration: false` | window.ts           | 页面拿不到 `require` / `process`              |
| 白名单 API               | preload/index.ts    | 页面能调用哪些能力完全由我们决定              |
| `setWindowOpenHandler`   | window.ts           | 外链交给系统浏览器，不在应用内开新窗口        |
| CSP                      | renderer/index.html | 限制脚本/样式/连接来源，阻断注入              |
| URL 协议校验             | ipc.ts              | `app:open-external` 只接受 http/https         |

## 七、目录约定

```
src/main/services/     ← 纯业务，不 import electron（store.ts 除外，它需要 userData 路径）
src/main/ipc.ts        ← 唯一注册 ipcMain 的地方
src/preload/           ← 唯一的 contextBridge
src/shared/            ← 只放类型与纯函数，禁止 import electron / node / DOM
src/renderer/src/lib/  ← 组合式函数（use*），可被任意组件复用
src/renderer/src/stores/ ← 全局状态，只在 App.tsx 里启动
```

`src/shared` 的「禁止 import 运行时 API」是一条硬约束——
它同时被 `tsconfig.node.json`（Node 类型）和 `tsconfig.web.json`（DOM 类型）编译，
一旦引入平台相关代码，两侧总有一侧会编译失败。这条约束顺便保证了它永远可测试。
